## Ambiguity and conflicting guidance

No direct conflict prevented a decision. The main boundaries were coherent: established architecture wins over new-app defaults; existing authorization carries forward; independent local work can proceed while an integration/device criterion remains open; and unrun acceptance never becomes a pass.

The following points require application context or careful interpretation:

1. **New-app choices.** Swift/SwiftUI is an explicit default, while deployment floor, persistence library, and design system are not selected for the reader. The skill supplies decision criteria rather than a concrete baseline. The field-journal plan therefore needs a recorded persistence/deployment choice; whether an OS-floor change is consequential depends on intended users. This is a gap to resolve from project context, not a reason to demand approval for every routine file or model choice.
2. **Implementation versus completion.** Note lifecycle permits an implemented note with device/release gaps, while Records forbids a complete phase with unmet required checks. Those are compatible statuses with different meanings, but a careless reader could use the note status as phase evidence. The continuity/evidence responses explicitly separate them.
3. **Readiness and deferral.** Plan allows an independent local phase to be ready despite a blocked later integration; Records requires explicit authorization to change required acceptance. Splitting upload work must not silently rewrite the original safe-retry promise or certify the whole feature. Likewise, absence of a device does not defer location background acceptance automatically.
4. **Product semantics remain inputs.** Location freshness/accuracy, cancel-versus-finalization semantics, durable undo history, offline saved-content guarantees, and media/performance budgets are not decided by the generic references. Plans/current contracts must own these decisions; arbitrary constants or inferred behavior would go beyond the evidence.
5. **Source of technical authority.** The iOS references link Apple/Swift material and require target-SDK verification. I loaded the local references but did not fetch external documents or verify specific APIs, because this exercise supplied no target implementation/toolchain and required next-work decisions. No claim of current SDK availability is made. Actual code choices must perform that check.
6. **Unavailable records.** The entry workflow asks to inspect current code and records. The scenario instruction explicitly provides no real app artifacts. I therefore describe those reads as next actions and do not claim I loaded fictional plans, source, runtime output, or screenshots. The only file created is this evaluation response.
